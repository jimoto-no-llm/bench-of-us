# Strata を sm_70 対応させ Tesla V100 32GB にエキスパート 2 万個を常駐させる

- **作成者**: eightman999
- **作成日**: 2026-09-29

## 概要

ローカル LLM エンジン [Strata](https://github.com/Niko1221/Strata)（Qwen3.8-Flash-Next 125B-MoE 専用の
GPU+RAM+SSD 分散エンジン）は CUDA `sm_80+` を要求し、Tesla V100（sm_70）は公式には対象外だった。
カーネル群を調査したところ sm_80+ 専用命令を使うのは未参照のデッドコード 1 ファイルのみだったため、
最小パッチで `sm_70` ビルドを作成し、V100 でのモデルロード・推論を確認した。

さらに、エキスパートキャッシュの常駐数が同梱プロファイルの 8,000 ペアで頭打ちになることを突き止め、
エンジン内のルーティング頻度テーブルをエクスポートするパッチを追加して 24,576 ペアの自作プロファイルを
生成。V100 の 32GB をほぼ使い切る **20,187 エキスパート常駐**を実現し、decode が 3060 比 1.7 倍に向上した。
追補として、`--mmap-experts` による RAM 34GB → 2GB 削減と、持続負荷下の温度・電力計測
（平衡 52°C・スロットリング無し）も記録した。

## sm_70 対応の調査と改造

### 調査結果

Strata の CUDA カーネル全ファイルを走査した結果、sm_80+ 専用命令を含むのは
`src/kernels/cuda/native_qsa_score.cu` のみ（`mma.sync.m16n8k8.row.col.f32.tf32` 系と `ldmatrix`）。
この関数は現行コード内に呼び出し元を持たないデッドコードだった。その他のカーネルは
BF16 独自ビット変換・FP16 半精度・汎用演算で構成され、sm_70 で実行可能。

### パッチ内容（ローカルのみ）

- `CMakeLists.txt`: `arch < 80` の FATAL_ERROR を緩和
- sm_70 ビルド時のみ `native_qsa_score.cu` をコンパイル対象から除外

以後の検証用パッチ（プロファイル生成のため。後述）

- `expert_source.hpp` / `expert_source.cpp` / `generate.cpp`: ヒット経路のルーティング記録フック、
  および `drive.d.usage`（適応キャッシュ機構が保持する 48×512 のルーティング頻度テーブル）を
  適応 tick ごとにファイルへ書き出すエクスポートを追加

## エキスパート常駐数の上限調査

Strata は `--expert-cache auto` で空き VRAM に応じてエキスパート blob（約 1.3MB/個）を GPU 常駐させるが、
実測では上限が **8,000 個**で止まっていた。原因は同梱の `data/expert-profile.bin` が 8,000 ランクペアしか
持たず、`auto` が `min(VRAM収容数, プロファイルペア数)` で決まるため。

対策として、エンジン内部の `drive.d.usage` テーブル（`--adapt-every/--adapt-swaps` 機構がデコード中に
維持する生のルーティング頻度）をダンプするパッチを追加し、30 種類の多様なプロンプト（日本語・英語・
コード・数学・技術文）で 8,516 トークンを生成して頻度を採取。頻度降順で 24,576 ペアをランク付けした
STRP 形式プロファイルを自作した。

採取した頻度の被覆率:

| スロット数 | 観測ルーティングの被覆率 |
|---:|---:|
| 8,000（同梱） | 99.4% |
| 12,000 | 100.0% |
| 24,576（全エキスパート） | 100.0% |

### 所感

- **sm_70 対応は実質不要に近かった**: sm_80+ 依存は未参照コードのみで、CMake ガードを緩めるだけで
  V100 がそのまま動いた。Strata の設計（重いエキスパート計算を GPU 側の汎用カーネルに寄せ、
  CPU/RAM/SSD を階層的に使う構成）はテンソルコア世代に依存しないためと思われる。
- **V100 フル活用はプロファイルが鍵**: 32GB の VRAM に 2 万エキスパートを常駐させると
  decode が 3060 の ~30 t/s から **~48-52 t/s** へ 1.7 倍に向上。CPU 側の expert drain がほぼ消えるため。
- 一方、頻度被覆率は同梱 8,000 プロファイルでも 99.4% あり、スロット増の効果は「残り 0.6% の
  CPU 計算を潰す」+「V100 の大容量を捨てない」という位置づけ。計測上は 32→48 t/s と効果大。
- **注意点**: 約 26k トークン超のプロンプトで HTTP 400 を返す制約がある（ctx 32K に対し実効上限が
  低い。原因未調査）。またエキスパート arena が RAM 約 34GB を占有するため、45.5GB 機では
  他の大型プロセスとの同時起動に注意が必要（実際、別インスタンスとの二重ロードで OOM ハングを
  一度経験した）。→ 後述の `--mmap-experts` 追補でこの RAM 問題は解消可能。
- 本ビルドとプロファイルパッチはローカル実験。`--dump-routing` 自体は上流にも存在するが、
  usage エクスポートは本調査のために追加した独自改造である。

## 追補: `--mmap-experts` による RAM 削減と熱負荷計測

### 背景

上記構成の弱点はエキスパート arena がプロセス RAM 約 34GB を専有すること（45.5GB 機で他系統と
共存しにくい）。Strata の `--mmap-experts` は `<pack>/experts.bin` を mmap してページキャッシュ経由で
供給する経路を持つため、`tools/iq_pack.py --experts-bin` でパックを作り直して検証した。

### 結果（V100、同じ 24,576 ペアプロファイル）

| 項目 | arena | mmap |
|---|---:|---:|
| プロセス実効 RAM | ~34 GiB | **~2 GiB**（expert 分はページキャッシュ管理） |
| 常駐エキスパート | 20,187 | 20,235 |
| decode @5.3k / @18.3k | 51.9 / 47.5 t/s | 50.2 / 46.3 t/s |
| prefill @5.3k / @18.3k | 430.6 / 487.4 t/s | 413.4 / 481.2 t/s |

GPU 側に 2 万エキスパートが常駐するため CPU 側 expert drain がほぼ発生せず、mmap の
ページング遅延は性能に実質影響しない（差は誤差範囲）。**34GB の RAM 壁は mmap 化で解消できる**。

### 熱・電力負荷（常駐運用の可否判断用）

上記 mmap 構成で 600 トークン生成を約 12 分連続実行し、`nvidia-smi` を 3 秒間隔で記録。

| 項目 | アイドル | 持続 decode 負荷 |
|---|---:|---:|
| GPU 温度 | 40°C | **平衡 ~52°C**（V100 上限 ~89°C に対し十分な余裕） |
| HBM 温度 | — | 最大 ~53°C |
| 消費電力 | 23.7W | 平均 ~91W / ピーク ~116W（TDP 250W の半分以下） |
| SM クロック | — | 1380MHz 一定、**スロットリング 0 回** |

PCIe 版 V100 はパッシブヒートシンクだが、本機の筐体風では平衡 52°C に収まった。
MoE の decode はメモリ帯域律速で電力が 80〜110W に跳ねるため、24/7 常駐の熱負荷は穏やか。

### 補足: マルチ GPU 分割について

「3060 + V100 の 2 枚でエキスパートを分割して RAM を減らす」案も検討したが、現行 Strata は
`DeviceArena` / `ExpertCache` / KV・verify バッファがすべて単一デバイス前提で、生成経路に
デバイス切替の仕組みがない。実現にはエンジン本体の構造改修が必要で、上記 mmap 化が
同等の RAM 削減を構造変更なしに達成するため、現状の合理的な解は mmap 側と判断した。
