# EVO-X2 128GBでQwen3.8-Flash-NextをHalogenで実行

- **作成者**: A-Uta
- **作成日**: 2026-09-26

## 概要

GMKtec NucBox EVO-X2（AMD Ryzen AI Max+ 395 / Radeon 8060S / 128GB unified memory）上で、Qwen3.8-Flash-NextをHalogen 0.14.0で実行した。

Halogenはllama.cpp / llama-serverベースではないため、bench-of-us標準の `llama-split-bench` は使用していない。代わりにHalogenのOpenAI互換API `/v1/chat/completions` が返す `timings` を使い、cold prefill、長Contextでのfull-context prefill / decode、実プロンプトdecode、32Kでのserial / MTP比較を測定した。

長Context測定では8K〜131Kの各contextを3回測定し、中央値とmin-maxを記載する。131K contextでもdecode中央値41.86 tok/sを維持した。32Kのserial / MTP比較では、MTPはserialに対してdecodeが **+22〜29%**（中央値比 **+28.8%**）高速で、temperature 0 / Thinking OFFの3組すべてで生成結果のSHA-256が一致した。

### 起動コマンド

```bash
podman --runtime=crun run --rm -p 8731:8731 \
  --device /dev/kfd \
  --device /dev/dri \
  --group-add keep-groups \
  --ipc=host \
  --ulimit memlock=-1:-1 \
  -e HALOGEN_KV_POOL_POSITIONS=262144 \
  -e HALOGEN_MAX_TOK=16384 \
  -v ~/models/Qwen3.8-Flash-Next-Halogen:/models:ro \
  ghcr.io/peonist-ai/halogen-flash-server:0.14.0
```

## セットアップ上の注意

Ubuntu 24.04環境のPodmanは当初 `runc` を使用しており、`--group-add keep-groups` では `/dev/kfd` の補助グループ権限をHalogenコンテナへ引き継げなかった。その状態ではHalogenが `no ROCm-capable device is detected` で終了した。

`crun` を導入し、`podman --runtime=crun ... --group-add keep-groups` で起動すると `/dev/kfd` と `/dev/dri/renderD128` をコンテナからopenでき、Halogenが正常起動した。

また、異常終了後にGTTが約7.6GiB残留し、`fuser -v /dev/kfd` では保持プロセスが見えない状態を1回確認した。原因は未確認。ホスト再起動後、GTT使用量は約179MiBまで低下し、その後は正常起動した。

## ベンチマーク

### 重要: prefill値の定義

本レポートの長Context prefill値は、**0〜N tokensを一括でprefillした全体平均速度**である。

`llama-split-bench` のdepth Nにおける **incremental prefill速度** とは定義が異なるため、prefill値は既存の `llama-split-bench` 結果とは直接比較しない。

decodeは「N tokens程度のcontext後に生成する速度」という意味では近いが、推論エンジンと測定方法が異なるため、こちらも完全な同条件比較ではない。

### Cold prefill

512 / 2048 / 8192 token級を各3回測定し、中央値を採用した。各runで `cache_n=0`。

| Actual prompt tokens | Prefill median tok/s |
|---:|---:|
| 563 | 384.69 |
| 2,100 | 699.14 |
| 8,244 | 991.52 |

### 長Context full-context cold sweep

8K / 32K / 65K / 131Kを各3回測定。各runで `cache_n=0`、各点で1,000 tokens生成を要求した。

| Target | Actual prompt median | Prefill median tok/s | Prefill min-max | Decode median tok/s | Decode min-max |
|---:|---:|---:|---:|---:|---:|
| 8K | 8,298 | 1,062.93 | 1,019.59–1,068.38 | 41.09 | 40.73–41.26 |
| 32K | 32,875 | 1,097.86 | 1,097.36–1,100.49 | 43.50 | 43.50–44.02 |
| 65K | 65,643 | 1,084.62 | 1,083.78–1,085.55 | 42.44 | 41.65–42.72 |
| 131K | 131,180 | 1,050.38 | 1,050.29–1,050.93 | 41.86 | 40.96–43.16 |

decode中央値は41.09〜43.50 tok/s、全runでは40.73〜44.02 tok/sだった。

`draft_n` / `draft_n_accepted` はHalogen APIが返すが、本レポートでは意味を独自に解釈せず、生値のみ保存した。単純比によるacceptance rateは算出していない。

### 8K付近のprefill差について

ほぼ同じprompt長で以下の差があった。

- Cold prefill: 8,244 tokens → 991.52 tok/s（3回中央値）
- 長Context測定: 8,298 tokens → 1,062.93 tok/s（3回中央値）

両者は入力内容、request形状、生成長、実行順が異なるため、同一条件での再現差とは扱わない。約7%の差の個別要因は未分離。

### 実プロンプトdecode

3種類のworkloadで各1,000 tokens生成した。

| Workload | Decode tok/s |
|---|---:|
| technical analysis | 41.12 |
| code review | 41.07 |
| agent workload | 40.85 |
| **3 workloadの中央値** | **41.07** |

この3値は同一promptの反復ではなく、3種類の異なるworkloadの測定値である。

### 32K serial vs MTP

32K級の同一promptを使い、request単位で `"drafter":"serial"` / `"drafter":"mtp"` を切り替えて3組比較した。測定中は他のHalogenリクエストを同時実行していない。

各pair内では同一promptを使用し、pairごとにnonceを変えた。順序偏りを減らすため、serial→MTP / MTP→serial / serial→MTP の順にした。

| Pair | Serial tok/s | MTP tok/s | MTP speedup | Output SHA-256一致 |
|---:|---:|---:|---:|---|
| 1 | 33.46 | 43.23 | 1.292x (+29.2%) | YES |
| 2 | 35.99 | 43.94 | 1.221x (+22.1%) | YES |
| 3 | 33.56 | 42.85 | 1.277x (+27.7%) | YES |

- Serial decode中央値: **33.56 tok/s**
- MTP decode中央値: **43.23 tok/s**
- MTPはserial比で **+22〜29%**、中央値比では **1.288x（+28.8%）**
- 3組すべてserial / MTPの出力SHA-256が一致

pair 2のみserialが2本目でprompt cache hit（`prompt_n=0`, `cache_n=32870`）しており、serialの最速値35.99 tok/sはこのrunである。3組のみの測定のため、prompt cacheの有無と実行順の影響は分離していない。

serial時は全runで `draft_n=0`, `draft_n_accepted=0`。MTP時は両カウンタが非ゼロとなり、request単位のdrafter指定が反映されたことを確認した。

同一pairの2本目はprompt cacheが利用されるため、このA/Bテストのprefill値はdrafter比較には使用せず、比較対象をdecode throughputに限定した。

生成本文は公開せず、SHA-256のみ保存した。

## 所感

Halogen 0.14.0 + Qwen3.8-Flash-Next W4Bは、今回のEVO-X2 128GB環境で8K〜131Kのfull-context cold prefill中央値が約1,050〜1,100 tok/s、decode中央値が41.09〜43.50 tok/sだった。

32Kの同一prompt A/Bでは、MTPはserialに対してdecodeが **+22〜29%**（中央値比 **+28.8%**）高速で、3組すべて生成結果のSHA-256が一致した。

Halogen公式reference環境や `llama-split-bench` の既存結果とはOS、Kernel、エンジン、prefill定義、`HALOGEN_MAX_TOK`などが異なるため、直接比較は行わない。
